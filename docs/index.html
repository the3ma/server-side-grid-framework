A grid is a contract, not a query.

How a regulated data portal went from five grid response shapes and a hand-written SQL builder per screen to one contract, one column allow-list and one SQL builder for SQL Server and Oracle. Every grid built on it pages, sorts and filters on the server in a way that cannot inject SQL, cannot widen a user’s row scope, refuses full-table scans and never shows an empty grid on failure. A public reference implementation in .NET 8 and Angular, generalized from production work.

Executive summary

The whole story in thirty seconds.

The problem

Every grid spoke its own dialect: five response shapes, pages counted from 0 or from 1, a stored procedure with no page-size cap and many grids that pulled every row into the browser. Each server-side grid hand-wrote its own SQL builder.

The approach

One request/response contract, a per-grid column allow-list, one SQL builder with SQL Server and Oracle dialects and one Angular data source. A new grid declares its columns once on each side.

The outcome

Paging, multi-sort, typed filters, set values and quick search on every grid built on it, with SQL that cannot be injected, a row scope that filters can only narrow, a server-side guard against full scans and typed errors instead of empty grids.

Every grid, its own dialect

Nothing was broken on any one screen. Across the portal, though, every grid had solved paging, sorting and filtering differently, and every new grid solved it again.

What every grid had to guarantee

In a regulated data portal a grid is a window onto controlled data. These guarantees are the acceptance test for the framework, and every grid inherits them.

  • One contractThe same request and response for every grid: page, page size, up to three sorts, typed filters, quick search, total on demand.
  • Safe by constructionNo request value is ever concatenated into SQL. Fields, operators and directions resolve only through the grid’s allow-list.
  • Row scope only narrowsWhat a user may see comes from their identity, never the request. Filters can remove rows from it, never add.
  • Same behaviour on both databasesSQL Server and Oracle produce the same rows for the same request, including escaping, blanks and null ordering.
  • Large datasets protectedFilters that can only full-scan are refused until an indexed filter narrows the set, and the UI explains why.
  • Never an empty grid on failureEvery error is typed and shown as an error. A grid that failed to load never looks like a grid with no data.
  • No values in URLs, logs or errorsFilter values travel only in POST bodies; logs and messages carry field ids, operators and counts.
  • Dates mean the same thing for everyoneRegulated record dates filter on UTC days; operational dates on the user’s own calendar.
  • Honest totalsA total that was not counted is unknown, not zero.
  • AccessibleErrors, hints and limits are announced to screen readers (WCAG 2.1 AA).

Who it serves

A shared framework has two kinds of users: the people who build grids and the people who use them. Compliance sits between the two.

Feature developers

Build the portal’s grids

Job
Ship a new paged, sorted, filtered grid without becoming a SQL-builder author.
Pain points
A new SQL builder, request mapper and stale-reply guard per grid; a different response shape each time.
What they got
Declare the columns once on each side; paging, filters, guard, cancellation and errors come with it. A worked example and a contract test.

Compliance & security

Own access control and data integrity

Job
Know that no grid can leak rows, columns or values, and that what users see is complete and true.
Pain points
Hand-written SQL per grid to review; values in URLs; empty grids that hid failures.
What they got
One allow-list to review, POST-only values, value-free errors, fail-closed restricted columns and null instead of a false zero.

Portal users

Search large, regulated datasets

Job
Find the right records quickly in grids with many thousands of rows.
Pain points
Grids that loaded everything first; one sort column; no way to tell a failure from no results.
What they got
Server paging, three sorts, typed filters with server-side value lists, a clear error banner with “Try again”, and a hint when a search is too broad.

The product

The public sample runs the framework on a synthetic warehouse shipment tracker: 80,000 rows for one tenant, a guarded grid and a restricted column.

Solution architecture

A feature owns two things: its column declaration and its base query. Everything between the click and the rows is shared, validated once and identical for every grid.

Decisions

Six architecture decision records, one per risk: injection, full scans, row scope, silent failures, time zones and invented numbers.

A per-grid column allow-list; no request value ever becomes SQL

ADR-0001
Context
A grid request names columns, operators and directions chosen by the browser. Every hand-written builder was a fresh chance of injection.
Decision
Each grid declares a static map from field id to a constant SQL expression. Requests only choose among entries; every value is a generated, bound parameter.
Result
Injection is impossible by construction. Snapshot tests prove request values never reach the SQL text on any dialect; unknown or malformed field ids are rejected before any SQL is built.

The large-dataset guard is a server rule, not a UI rule

ADR-0002
Context
contains, endsWith and free-text search can’t use an index. Hiding them in the UI protects nobody who calls the API directly.
Decision
On a guarded grid they are refused with 400 grid-filter-too-broad unless an indexed filter narrows the set. Every page reports capabilities to the UI.
Result
No caller can start a full scan, and users see why a search was refused and what to filter first.

Wrap the base query; filters can only narrow the row scope

ADR-0003
Context
Row-level access lives in each grid’s base query. Splicing filters into its WHERE risks an OR that widens it.
Decision
The base SQL becomes derived table g; filters, sort, tiebreaker and paging are applied outside it. Scope parameters come from the identity only.
Result
A filter can only remove rows a user may already see, and paging is stable.

Typed, value-free errors; a failure is never an empty grid

ADR-0004
Context
An empty grid reads as “no data”, a data-integrity problem. Messages that echo a filter value put it into logs.
Decision
Four ProblemDetails types with field-level codes and no values. The UI shows an inline alert with “Try again”.
Result
Failures are visible, and logs carry ids, operators and counts only.

Date semantics belong to the column, not the client

ADR-0005
Context
“3 March” is a different instant in Tokyo and New York, and browsers shift parsed dates silently.
Decision
Each date column is utc, local or calendar; the client sends plain YYYY-MM-DD; every range is half-open.
Result
Regulated dates filter identically for everyone; operational dates match the user’s day.

A total is null when not counted; a malformed page is an error

ADR-0006
Context
Counting can cost as much as the page; a “0” for an uncounted total is a false statement.
Decision
Count only on request, else null. Parse every page strictly; one bad row fails the page.
Result
Paging forward costs one query, and no number on screen is invented.

Trade-offs

A framework that is safe by construction says no to some things. These are the costs accepted on purpose.

ChoseInstead ofThe cost, and why it’s worth it
A declared allow-list per gridA generic query language over any columnEach column is declared on both sides. A manifest test catches drift, and the review surface for security is one map.
A server-side scan guardTrusting the UI to keep searches reasonableSome searches are refused until the user narrows by an indexed column; the UI says which ones.
One condition per field, AND across fieldsThe grid’s two-condition and OR filtersLess expressive, but the client fails loudly instead of sending something the server would read differently.
No caching of grid queriesThe portal’s query cacheEvery page hits the database. A cache key not built from the full request, row scope and column access would serve one user’s rows to another.
Count only on requestA total with every pageThe UI keeps the last known total while paging, so it can briefly be stale, but it is never invented.
Columns must be SQL expressionsValues computed in application codeA derived label has to move into SQL before its grid can adopt the framework; otherwise it can’t be sorted or filtered on the server.

Results

Every guarantee maps to a mechanism, and every mechanism has a test layer.

  • One way to build a gridA column declaration on each side and a base query. Paging, multi-sort, five filter types, set values, search, guard, cancellation and errors come with it.
  • Injection-safe by constructionSQL and parameter snapshots for each dialect prove hostile values never reach the SQL text; guard and API tests reject unknown and malformed field ids.
  • Large grids protectedFull scans are refused on the server and explained in the UI.
  • Failures that look like failuresTyped errors and an inline banner; never an empty or partial grid.
  • Contract drift caught earlyThe backend emits a manifest of each map; the frontend test fails when its declaration differs.
  • AdoptedThe first grid moved onto the framework: an administration grid.

Try it yourself

The sample runs locally with no database server: the API seeds a SQLite file with 120,000 synthetic shipments on first start.

$ git clone https://github.com/the3ma/server-side-grid-framework.git
$ cd server-side-grid-framework
$ dotnet test                          # 108 tests: guard, SQL snapshots x3 dialects, dates, API
$ dotnet run --project src/SampleApi   # http://localhost:5080, seeds 120,000 shipments
$ cd web && npm ci && npm start        # http://localhost:4200 through the dev proxy

No .NET? cd web && npm ci && npm run start:mock runs the UI against an in-memory backend with the same rules. The request and response rules are in the grid contract.

Lessons

What carries over to the next shared component in a regulated product.

  • Make the safe path the only path.An allow-list that every grid must declare beats a review checklist that every grid must pass.
  • Put a rule where every caller passes.A limit enforced in the UI is a suggestion; on the server it is a guarantee.
  • Snapshot tests prove the SQL, not the types.A column mapped with the wrong type passes every snapshot. One database-backed test per grid is what catches it.
  • Unknown is not zero.An empty grid and a false total both look like answers. In regulated data they have to look like what they are.

What’s next

Deliberate limits today, and the open questions they leave.

  • Server-side exportsAn export of a server grid can only contain the loaded page, so data-source grids need a server export path. That path is its own case study: the async export pipeline turns an export into a streamed, audited job.
  • Cross-database columnsPage and count run on one connection; a column from another database can be shown, not sorted.
  • Pure reads onlyA list endpoint that writes during the read can’t page; those reads need to be split first.
  • Open defaultsCollation, the 30-second timeout, per-grid thresholds, a minimum search length and nvarchar binding on varchar columns.
